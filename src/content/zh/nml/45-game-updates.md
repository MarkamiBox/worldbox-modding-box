# 游戏更新后更新你的 mod :wbsettingsgear:

WorldBox 更新了，你的 mod 在列表里变红了。欢迎来到模组开发，这事每个人都会遇到，以后还会再遇到 :PES2_Shrug:。

你的 mod 调用的是游戏自己的代码。开发者一旦重命名某个方法、挪动某个字段，或者改了方法接收的参数，你的代码就指向了一个已经不存在的东西。它不是彻底坏了，只是过时了。这一页就是我每次排查的顺序。

## 1. 先更新 NML

在动你自己的代码之前，先去 **[安装 NML](#/install-nml)** 页面下载最新的 **`NeoModLoader.dll`**。游戏大更新通常也会带来新版 NML，而旧加载器跑在新游戏上时出的错，看起来跟你自己的错一模一样。

如果连 NML 本身都加载不了，那还没轮到你的 mod。先看故障排除里的 **[游戏处于旧版本](#/troubleshooting)**，然后再回来。

## 2. 读第一个错误

启动游戏，然后打开 `Player.log`（位置见 **[日志与调试](#/nml/logs-and-debugging)**）。找到你的 mod 的第一个错误，下面的先全部忽略。错误会连锁出现，修好第一个往往能让另外五个一起消失。

更新之后你最常看到的是这些：

| 错误 | 游戏里改了什么 |
| --- | --- |
| `CS0117: 'X' does not contain a definition for 'Y'` | 某个字段或静态方法被重命名或删除了 |
| `CS1061: 'X' does not contain a definition for 'Y'` | 同上，但是在对象上：`actor.someMethod()` 没了 |
| `CS0246: The type or namespace name 'X' could not be found` | 整个类被重命名或移动了 |
| `CS7036` / `CS1501` | 方法还在，但现在接收的参数不一样了 |
| `CS0122: 'X' is inaccessible due to its protection level` | 你用到的东西变成了 `internal`，见 **[那一条](#/troubleshooting)** |
| `CS0029` / `CS0266` | 某个字段换了类型，比如从 `int` 变成 `float`，或从字符串变成资产 |
| 启动时出现 `HarmonyException` / `MissingMethodException` | 你 **patch** 的方法被重命名了。代码能编译，但补丁没有地方可挂 |

最后一个最阴险。用普通字符串写方法名的补丁，比如 `"updateStats"`，只在游戏启动时才检查。所以改名不会让你的 mod 编译失败，而是让它不起作用。用 `nameof` 写的补丁则会得到一个普通的编译错误，这也是能用就用它的又一个理由（**[方法名的两种写法](#/nml/harmony-patches)**）。

## 3. 找到新名字

旧名字没了，就去找它的替代品：

- 本站的 **[方法搜索](#/tools/methods)**。输入这个方法*做了什么*，而不是它叫什么："add trait to unit" 即使名字变了也能找到。
- 资产字段用 **[资产字段](#/tools/fields)**。搜你还记得的那部分名字。
- **dnSpy**，它永远是对的，因为它读的就是你手上的游戏。本站的搜索工具会在更新后重新生成，但对刚出的更新可能会晚几天。用法见 **[阅读游戏代码](#/toolbox/reading-the-game-code)**。

我最常用的技巧：打开跟你的东西做同样事情的原版资产或方法，看看**游戏自己**现在是怎么写的。如果游戏改了特质的创建方式，它自己的特质已经在用新写法了 :PESgn_Noice:。

## 4. 手动检查你的 Harmony 补丁

补丁也可能在没有任何报错的情况下出问题。逐个检查，并在 dnSpy 里核对方法：

- **参数名。** Harmony **按名字**填充参数。如果游戏把 `pDamage` 改成了 `pAmount`，你的 `float pDamage` 就会悄无声息地什么都拿不到。见 **[神奇的参数名](#/nml/harmony-patches)**。
- **重载。** 以前唯一的方法现在可能多了一个同名的，你的补丁会报 `Ambiguous match found`。
- **方法做的事。** 有时候名字没变，逻辑却搬去了别处。补丁照常运行，但什么也没改变。在补丁里加一行 `LogInfo`：如果它从来不出现，说明游戏已经不再调用这个方法了。

## 5. 找出不再起作用的东西

重新能编译不是终点。载入一个世界，检查每一部分是否还正常：特质显示图标，物品会掉落，神力会生成该生成的东西。

新的更新可能加了一个字段，原版资产现在都会填，而你的没有。资产能加载，没有报错，就是什么都不做。把你的资产和它所在库的 `init()` 里最相似的原版资产逐个字段对比。游戏现在设置了而你没设置的，就是嫌疑对象。

## 6. 也测一个旧存档

开着你的 mod，载入一个在更新**之前**保存的世界。存在单位上的自定义数据（**[保存数据](#/nml/saving-data)**）应该原样回来。如果你在修复时改了某个 id，旧存档里用的还是旧 id，所以除非真的必要，别改名。

## 7. 发布

- 把 `mod.json` 里的 `version` 调高。
- 在描述和更新日志里写明它适配哪个游戏版本，让玩家知道该下哪个。
- 像之前一样上传新的 zip：**[发布](#/nml/publishing)**。

然后去回复那些"更新了吗？？"的评论，这是你应得的 :wbsalut:。

## 让下一次更新少痛一点

- **少打补丁。** 每个 Harmony 补丁都是一个可能坏掉的点。如果资产字段或 NML 的功能能做到，就用它们。
- **把代码包进 try/catch。** 一个功能坏了只会在日志里写一条错误，mod 的其余部分照常工作。见 **[日志与调试](#/nml/logs-and-debugging)**。
- **一个任务一个补丁类。** 一个补丁坏了，只会掉一个功能，而不是全部。
- **把 id 放在一个地方。** 像 `HelloTraits.SWIFT` 这样的常量，让改名只需要改一处，而不是二十处。
